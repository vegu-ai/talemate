# Bulk visibility assessment

The director's chat-only `assess_visibility` action assesses authored entry visibility on an explicit user request. It uses the existing action framework and `ActionConfirm`, with no scene lifecycle hook, activation migration or background sweep. Both legacy and Character perspectives stories support it.

`VisibilitySelection` accepts `scope` (`attributes`, `details`, `world_entries`), one `character` for sheet scopes, explicit `world_entries` names or Context IDs for the world scope, `instructions`, and `reassess` (default false; native booleans and canonical true/yes/1 or false/no/0 strings only, validated from the raw action argument). Internal, name and scenario_context attributes are excluded by the shared authored-memory predicate. Empty world selections never expand to all entries; invalid or oversized selections fail before generation. The host accepts at most 32 eligible entries after restriction/empty filtering and rejects a rendered prompt exceeding the smaller of the client budget or 16,384 tokens, reserving up to 4,096 tokens (one third of the budget on smaller clients) for output. It includes up to 2,048 tokens of author history, capped at one quarter of the client budget, plus description, intentions and cast. Client section formatting and deduplication apply before token measurement. A fixed-context refusal identifies context/instructions separately from an oversized entry selection. This is bounded context, not exhaustive discovery of every relevant event.

`VisibilityAssessmentMixin.assess_entry_visibility` snapshots selected content, object identity and current visibility. Non-everyone restrictions are excluded unless reassessment was requested. It makes one director analytical request for eligible entries. The template requests structured decisions (`set`, `mixed`, `uncertain`); local JSON extraction accepts common wrappers and repairs separator mistakes without model-assisted repair; a strict proposal schema requires an explicit visibility mode and forbids unknown fields. Duplicate, missing, invalid or out-of-scope decisions cannot mutate those entries. Valid decisions for other selected entries can still proceed. The host validates audience modes and resolves existing character names using the same whitespace/case/comma handling as the single-entry action; semantic classification and faithful interpretation of the user's reassessment request remain the model's responsibility.

Mixed-content decisions produce split/manual-correction feedback and no proposed mutation. An entry already marked everyone can therefore remain overexposed until the author corrects it. This is an authoring aid, not a complete privacy detector or proof of containment. Sheet owners retain their implicit access, and owner mode on a world entry means nobody.

Both model inputs and reports include readable entry names (detail questions included). Reports show both old and proposed audiences with the existing Known by formatter, including implicit owner access and nobody for ownerless private entries. Validation diagnostics identify the field or failure reason; expected action failures reach director chat through `ActionFailed`.

The shipped graph passes the nonempty plan through one normal `ActionConfirm`, then `ApplyVisibilityAssessment`. No-op reports bypass confirmation. The existing per-chat confirmation setting controls approval; no per-entry approval is added. Plans are ephemeral and single-use, with scene identity, cast membership and selected content/visibility checks before application. A scene switch or stale batch cancels remaining writes rather than silently reassessing. Changes use `WorldStateManager.set_character_entry_visibility` / `set_world_entry_visibility`, preserving normal K08 audience-index invalidation, then emit the normal World Editor refresh. No text, grants, disclosures or revokes are rewritten.

See [Director Chat](../user-guide/agents/director/chat.md#assess-visibility-in-bulk) for invocation and correction examples.
